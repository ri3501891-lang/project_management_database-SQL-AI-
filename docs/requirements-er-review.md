# 要件整理・エンティティ・リレーション整理の振り返り



このドキュメントでは、要件整理・エンティティ抽出・リレーション整理の段階で、自分が最初に考えた案と、あとから修正した内容を振り返る。

## 題材

題材は「ITプロジェクト管理システム」にした。  
ただし、最初から詳細な仕様を与えるのではなく、あえて曖昧でざっくりした顧客要件から設計を考える練習にした。

## ざっくりした要件

- プロジェクトごとにタスクを見たい
- 誰がどのタスクを担当しているか分かるようにしたい
- 遅れているタスクが分かるようにしたい
- 優先度のような情報も見られるようにしたい
- 最初はシンプルな構成でよい

## 最初の自分の案

### エンティティ
- project
- tasks
- assignee

### リレーション
- project と tasks が 1対多
- tasks と assignee が 多対多
- projects と assignee が 多対多

## 最初の案で良かった点

- project / tasks / assignee という主要なエンティティを分けて考えられた
- project と tasks の関係を 1対多 と判断できた
- tasks と assignee の関係を、多対多の可能性として捉えられた
- projects と assignee の関係も、多対多の可能性として考えられた

## 最初の案で不足していた点

- 多対多を、そのままテーブル間の関係として考えていて、中間テーブルへの分解ができていなかった
- project_assignee と task_assignee のような中間テーブルが必要なことを最初は整理できていなかった
- 「概念上の関係」と「論理設計上のテーブル構成」を区別できていなかった

## AIの添削で学んだこと

- 多対多は、そのままではRDBのテーブル構成に落としにくい
- 多対多は、中間テーブルを追加して、1対多の組み合わせに分解する
- 概念設計では「多対多」で考えてよいが、論理設計では中間テーブルが必要になる
- projects と assignees の関係は、要件次第では task_assignees だけで表現できる場合もある
- ただし、「まだタスク未割当の参加者も管理したい」なら project_assignees が必要になる

## 修正版の案

### エンティティ / テーブル
- projects
- tasks
- assignees
- task_assignees
- project_assignees

### リレーション
- projects 1 - N tasks
- tasks 1 - N task_assignees
- assignees 1 - N task_assignees
- projects 1 - N project_assignees
- assignees 1 - N project_assignees

## 最終的な理解

最初に考えた「project / tasks / assignee」という分け方自体は悪くなかった。  
ただし、多対多の扱いを論理設計に落とすときには、中間テーブルが必要だった。

今回の振り返りで、以下の違いを意識できるようになった。

- 要件から見た業務上の関係
- ER図上の関係
- 実際のテーブル構成

## 今後の改善ポイント

- 多対多を見つけたら、中間テーブルが必要かをすぐ考える
- 概念設計と論理設計を分けて考える
- 「その関係は本当に必要か」を、要件から考える
