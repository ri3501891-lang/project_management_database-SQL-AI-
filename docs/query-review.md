# SQLレビュー（悪いクエリ5本）の振り返り



このドキュメントでは、あえて不便に書かれたSQL 5本について、自分が分かったこと・分からなかったこと・AIの解説を整理する。

## Query 1: プロジェクトごとの完了率

### 自分が気づけたこと
- サブクエリが多いことには気づけた。

### 自分が分からなかったこと
- どのように直せば効率が上がるのか分からなかった。

### AIの解説
- このクエリは、同じ `tasks` テーブルに対する件数集計を何度も繰り返している点が非効率だった。
- `total_tasks` と `done_tasks` を求めるために似たようなサブクエリを複数回実行しており、同じ計算を重複して行っている。
- 相関サブクエリは外側の行ごとに評価される形になりやすく、データ件数が増えると負荷が大きくなる。
- 改善するなら、`projects` と `tasks` を `JOIN` し、`GROUP BY` で一度に集計する形に直すのが自然。

### 修正方針
- 相関サブクエリを減らす。
- `JOIN + GROUP BY` で1回の集計にまとめる。
- 同じ `COUNT(*)` を何回も書かない。

## Query 2: メンバーごとの担当タスク数

### 自分が気づけたこと
- 分からなかった。

### 自分が分からなかったこと
- どこが悪いのか判断できなかった。

### AIの解説
- このクエリは、古いJOIN記法を使っていて読みづらい。
- `JOIN ... ON ...` を明示的に書く方が、どのテーブルがどう結合されているか分かりやすい。
- `COUNT(DISTINCT t.taskid)` を使っているが、これは重複の原因を整理しないまま重複を隠している可能性がある。
- `GROUP BY` に同じ列が重複して書かれているのも無駄。
- まずは JOIN を分かりやすく書き直し、その上で `DISTINCT` が本当に必要かを確認するべきだった。

### 修正方針
- 古いJOIN記法をやめて `JOIN ... ON ...` にする。
- `GROUP BY` の重複をなくす。
- `DISTINCT` を使う前に、なぜ重複が発生するか確認する。

## Query 3: 遅延タスク一覧

### 自分が気づけたこと
- 外部結合を複数回使っていて、出したい行を出せない可能性があると思った。

### 自分が分からなかったこと
- どの結合を外部結合にするべきか、どこを内部結合に直すべきかまでは分からなかった。

### AIの解説
- `LEFT JOIN` は、結合先のデータがなくても左側の行を残したいときに使う。
- しかし、このクエリは担当者名やプロジェクト名つきで遅延タスクを出したい意図に見えるため、すべてを `LEFT JOIN` にする必要があるとは限らない。
- 結合条件が曖昧だと、想定しない `NULL` 行が混ざったり、結果の意味が分かりづらくなる。
- WHERE句の条件も回りくどく、遅延の定義が曖昧になっていた。
- 「期限を過ぎていて、まだ完了していないタスク」のように、業務ルールを明確にした方がよい。

### 修正方針
- 本当に NULL を許したい結合だけ `LEFT JOIN` にする。
- 必須の関連なら `INNER JOIN` を検討する。
- WHERE句は業務ルールに合わせて単純にする。

## Query 4: ステータス×優先度の件数

### 自分が気づけたこと
- 分からなかった。

### 自分が分からなかったこと
- 何が悪いのか判断できなかった。

### AIの解説
- このクエリは、一見大きく壊れてはいないが、書き方が回りくどい。
- 同じ `CASE` 式を `SELECT` と `GROUP BY` の両方に書いており、同じ式が重複している。
- 件数を出すのに `SUM(CASE WHEN taskid IS NOT NULL THEN 1 ELSE 0 END)` としているが、`taskid` は主キー想定なので通常は NULL にならない。
- そのため、ここは `COUNT(*)` で十分であり、その方が読みやすい。
- 処理自体は単純なのに、SQLの見た目だけが複雑になっているタイプだった。

### 修正方針
- 同じ式の重複を減らす。
- 件数集計は `COUNT(*)` で済むならシンプルに書く。
- 「やりたいことに対して最短の書き方か」を意識する。

## Query 5: 特定メンバーの今月タスク＋遅延フラグ

### 自分が気づけたこと
- 分からなかった。

### 自分が分からなかったこと
- サブクエリが不要な理由や、どこを簡単にできるのか分からなかった。

### AIの解説
- このクエリでは、外側で `tasks t` を読んでいるのに、`is_overdue` を出すためだけにサブクエリ内で `tasks t2` をもう一度読んでいる。
- これは同じタスクの情報を二重に読んでいる状態で、無駄がある。
- 遅延フラグは、外側の `t.due_date` と `t.status` をそのまま使って `CASE` 式を書けば十分。
- わざわざ別の `tasks` を読み直す必要はない。
- 「今ある行の情報だけで判定できるなら、その場で計算する」という考え方が大事。

### 修正方針
- 不要なサブクエリを削除する。
- `CASE` 式は外側の列をそのまま使う。
- 同じテーブルを同じ目的で何度も読み直さない。

## 全体を通して学んだこと

- 相関サブクエリは便利そうに見えても、同じ計算を何度も繰り返してしまうことがある。
- JOIN は `JOIN ... ON ...` の形で明示的に書いた方が読みやすい。
- `DISTINCT` はとりあえず使うのではなく、重複の原因を先に考えるべき。
- `LEFT JOIN` は「とりあえず使う」のではなく、NULL を残したい場合だけに使う。
- SQLは「動くか」だけでなく、「同じことをもっとシンプルに書けないか」で見直すことが大事。
